# Rust Library API Map

The Rust API is documented alongside this map in the module pages generated by rustdoc. This section explains where to start and which build features make each part available.

## Choose a build feature

| Feature | What it enables | Status |
| --- | --- | --- |
| No feature | Base library types and APIs that do not require the native desktop runtime. | Default build. |
| `native` | Native desktop windows, system integration, and application runtime support. | Windows is the currently supported native platform. |
| `cef` | Optional CEF renderer integration. | Requires a matching CEF runtime and additional packaging. |
| `experimental-language` | The custom Poly language lexer, parser, interpreter, and source execution functions. | Experimental and excluded from the default build. |
| `experimental-virtual-drive` | The NCOS Virtual Drive and its filesystem integration. | Experimental and Windows-first. |

Add features explicitly when building or installing the crate:

```sh
cargo add poly-framework --features native
cargo add poly-framework --features "native experimental-language experimental-virtual-drive"
```

## Main API areas

| Area | Rust modules and entry points | Purpose |
| --- | --- | --- |
| Application runtime | [`native`](crate::native), [`config`](crate::config) | Configure and run desktop application windows and read `poly.toml` settings. |
| Window and embedded content | [`window`](crate::window), [`webview`](crate::webview), [`webview_native`](crate::webview_native), [`browser`](crate::browser) | Manage windows, browser surfaces, navigation, and events. Native operations require `native`. |
| Multiple views | [`multiview`](crate::multiview), [`multiview_native`](crate::multiview_native), [`polyview`](crate::polyview) | Create and coordinate multiple web content views. |
| System integration | [`clipboard`](crate::clipboard), [`notification`](crate::notification), [`tray`](crate::tray), [`deeplink`](crate::deeplink), [`hotkeys`](crate::hotkeys) | Connect an app to host features such as clipboard, notifications, tray menus, URL protocols, and hotkeys. |
| App services | [`updater`](crate::updater), [`permissions`](crate::permissions), [`single_instance`](crate::single_instance), [`cookies`](crate::cookies), [`db`](crate::db) | Updates, permission configuration, single-instance handling, cookies, and local data. |
| Web helpers | [`web`](crate::web), [`templates`](crate::templates), [`adblock`](crate::adblock), [`adblock_engine`](crate::adblock_engine), [`adblock_init`](crate::adblock_init) | HTML helpers, starter templates, and optional content filtering services. |
| AI integration | [`ai`](crate::ai) | Provider configuration and chat request and response types. |
| CEF renderer | [`cef_osr`](crate::cef_osr), `cef_api` | Optional Chromium renderer integration. Requires the `cef` feature. |

The crate root re-exports frequently used types and functions. For example, `NativeConfig`, `run_native_window`, `UpdateConfig`, `TrayConfig`, and `AiProvider` can be imported directly from `poly_framework`.

## JavaScript API

Most Poly app developers use the JavaScript bridge exposed to the frontend instead of calling Rust functions directly. The [Complete JavaScript API Guide](#complete-javascript-api-and-developer-guide) below describes those APIs, project setup, platform requirements, and known limitations.

## Experimental language

The custom language has its own built-in functions and interpreter APIs. Its full reference is included in the [Experimental Poly Language API](#experimental-poly-language-api) section below. These APIs may change without compatibility guarantees.
